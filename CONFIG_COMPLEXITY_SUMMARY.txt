HOLOLOOM CONFIGURATION COMPLEXITY ANALYSIS SUMMARY
===================================================

KEY METRICS
-----------
Total Parameters: 72
Master Switches: 14
Dependent Parameters: 31
Never-Customized: 19 (26% waste)
Configuration Complexity: 6.5/10 (moderate-high)

TOP 3 HOTSPOTS
---------------

1. MEMORY BACKEND (11 params, 70% waste)
   - Backend-specific params are flat, not nested
   - Dead code: mem0_* (3 unused params)
   - When using INMEMORY: 8+ orphaned parameters

2. PHYSICS PARAMETERS (7 params, all hardcoded)
   - use_spring_activation = False (disabled default)
   - 5 physics constants never tuned in practice
   - Creates cognitive overhead even when disabled

3. FEATURE FLAG CASCADE (5 masters, 31 dependents)
   - Master switches with orphaned dependent params
   - enable_linguistic_gate -> 7 child params
   - enable_semantic_calculus -> 6 child params
   - enable_recursive_learning -> 6 child params
   - use_spring_activation -> 6 child params
   - enable_beta_wave_packing -> 5 child params

PROBLEMATIC INTERDEPENDENCIES
------------------------------
- No validation of orphaned parameters
- No backend availability checks
- No conflict detection (mode vs subsystem)
- Multi-scale code disabled but still referenced

VALIDATION GAPS
----------------
What IS validated:
  scales sorted ascending
  fusion_weights sum to ~1.0
  hyperspace_thresholds match depth
  mode string -> ExecutionMode enum

What's NOT validated:
  Interdependency conflicts
  Backend availability (Neo4j/Qdrant)
  Environment variables
  Multi-scale consistency

FACTORY METHODS
----------------
Config.bare():   1 layer, 2 heads, minimal (2 uses)
Config.fast():   2 layers, 4 heads, Phase 5 (11 uses - most common)
Config.fused():  2 layers, 4 heads, Phase 5, semantic (8 uses)

Issue: fast() and fused() nearly identical (only semantic_dims differ)

ACTUAL USAGE
-----------

  Config.fast():    11 uses
  Config.fused():   8 uses
  Config.bare():    2 uses
  Custom Config():  rare
